# 加载链路优化（2026-11-23）

源码已修改，尚未重新生成抖音包。当前 build/douying 仍是 11 月 20 日构建；loading-audit 中的文件大小来自该构建，耗时表为估算。

## 实际发现

- 章节是普通远程 Bundle，不是 ZIP 或平台分包。`loadBundle` 只取清单和本地脚本入口，并不主动取回所有图片。但这并不意味着业务只请求了当前关卡。
- 打开选关页时，`showLevelSelect → ensureCity` 原来会串行调用全章 `_ensureLevel`，青花瓷为 60 个玩法配置请求。任何一个尚未游玩的配置失败也会阻塞整章选关。
- `startLevel` 原来先等玩法界面完成，再加载关卡配置、发现章节音乐和连击索引，最后在 `setupLevel` 内依次加载上下两张图片。
- 玩法界面内部还会先等 GameplaySupport 加载和实例化，再请求 GameScreen 与 ResultModal。
- 下一关预下载通过 `_loadLevel` 读取配置后没有填入单关缓存；正式进入时会再次走配置加载（引擎可能命中磁盘/内存缓存，不能等同于一定重新走网络）。

## 修改后

- `ensureCity` 从主包章节清单生成独立 `levelCards`，包含永久 ID、名称及标准缩略图路径；完整差异点仍只由 `_ensureLevel` 按需加载。已核对 390 个缩略图均存在，选关仍只加载当前页封面。
- `levelCards` 与 `levelConfigs` 分离，避免将没有差异点的展示数据当成可玩的关卡配置。星级、解锁、章节顺序和翻页仍使用原永久 ID 与关卡索引。
- 进入关卡时并行准备共用界面、单关配置、章节音乐索引和连击索引；章节清单仍由 ContentBundlePool 合并请求。章节音频本体按需播放加载。
- GameplaySupport、玩法和结算预设并行请求，但全部就绪后才创建依赖它们的玩法节点。
- 两张大图并行加载，按上/下固定位置绑定；单图先完成不会提前显示玩法。失败时等待另一请求收尾并释放所有已取得的引用，退出后的迟到资源同样释放。
- `_ensureLevel` 合并同一城市、同一关卡的在途配置请求；失败移出在途缓存，允许重试。下一关预下载使用该接口，正式进入复用配置。
- 下一关图片仍串行、低优先级预下载。后续应用户要求另加了按章节顺序预下载全项目的后台队列，该队列让当前关卡和下一关预取优先，详见 `README-background-assets-2026-11-23.md`。

## 新包实测

开发者工具控制台设置：

```js
globalThis.__findDifferenceLoadingDebug = true;
```

编辑器浏览器预览默认输出 `[LevelLoad]` 和 `[SelectionLoad]` 概要，不需要手工开启开关或打抖音包。刷新 Creator 的脚本后重新加载预览页面即可；发布包仍需重新构建。开启上面的开关会额外启用图片细分诊断。也可读取：

```js
globalThis.__findDifferenceLastLevelLoad
```

字段为 `chapterKey`、从 0 开始的 `levelIndex`、`status`、`totalMs`、`uiMs`、`configMs`、`musicIndexMs`、`comboIndexMs`、`imagesAndSetupMs`、`loadingFrameMs`、`firstGameFrameMs`。各阶段包含引擎缓存查找和相关等待，是墙钟耗时；并行阶段不能直接相加，也不是纯网络下载时间。总耗时从关卡加载遮罩启动后到本次加载结束，不包含引擎启动、主包下载或前面的选关页加载。`prepared` 可表示 Feed 预览就绪但尚未正式开始，`ready` 表示已开始。

开启诊断模式时，记录还包含 `bundles`（实际调用 loadBundle 的清单加载记录）和 `images`（每张关卡图的细分记录）。清单记录不等同于下载整章资源。历史记录分别存放在 `__findDifferenceBundleLoads` 和 `__findDifferenceImageLoads`，每组最多 64 条；没有新增清单记录可能只是复用已加载/在途的清单，不代表全部图片已有缓存。

每张图的 `bundleWaitMs` 是取得清单的等待，`filesReadyMs` 是 `preloadAny` 的资源预取耗时（包括网络或磁盘缓存读取、依赖清单等），`assetReadyMs` 是文件预取后到 SpriteFrame 可用的耗时，包含解析、解码和资源构建，不能单独当成 GPU 耗时。首次渲染和 GPU 上传还可能体现在 `firstGameFrameMs`。`memoryCached` 只表示开始预取时 SpriteFrame 是否已在引擎内存缓存；false 不能证明磁盘未缓存。

为拆开这些阶段，**仅开启诊断时**额外执行一次 preloadAny，再执行原来的 bundle.load。普通玩法不增加该步骤。诊断耗时用于定位，不能和未开启诊断的总耗时直接做严格性能对比。文件阶段较慢时仍需结合抖音开发者工具 Network 的请求、耗时和重试确认是否卡在网络，不将磁盘读取误判成 CDN 下载。

进入章节选关页会另行记录 `globalThis.__findDifferenceLastSelectionLoad`，开启诊断时输出 `[SelectionLoad]`，包含 `indexMs`、`pageMs`、`totalMs`。这里的页面就绪不代表异步的当前页缩略图都已显示。选关页耗时与关卡加载总耗时分开，避免混算。

观察方法：在进入尚未访问的章节前开启诊断，分别记录第一次、同章下一关、重玩同一关的日志。`uiMs` 高说明共用界面依赖或实例化慢；`bundleWaitMs` 高说明清单环节慢；`filesReadyMs` 高说明资源预取慢；`assetReadyMs` 或首帧等待高则检查解析/解码/渲染。多阶段可能重叠，不按各项之和推断总耗时。

这次没有修改下载服务器或资源打包压缩方式，也没有宣称确定的提速秒数。新包应分别测首次无缓存、同章下一关、跨章进入和返回重玩；旧包不会包含本次修改。

## Cocos 本地预览复测

2026 年 11 月 23 日在当前运行的 Creator 3.8.8 本地预览（localhost:7456）加载最新源码，直接从预览控制台读取阶段计时。没有清理浏览器缓存，也没有恢复原串行版本做同条件对照，因此不能将下表当成无缓存首次下载的基准，或宣称所有设备都已消除 2–5 秒等待。

|重载页面进入网络热点第 2 关|531 / 549 ms|共用界面 423 / 453 ms，图片设置 40 / 45 ms|

本次样本未复现 2–5 秒。用户指出除第一章之外基本都会首次慢；这与代码中两条入口的差异吻合：启动 `startContinue → startLevel` 原本仅读当前关，而从章节入口 `showLevelSelect → ensureCity` 原本串行读全章配置。已移除后者的整章配置阻塞，但还不能证明它是所有延迟的唯一原因。原始观测记录见 `loading-audit/cocos-preview-2026-11-23.json`。
